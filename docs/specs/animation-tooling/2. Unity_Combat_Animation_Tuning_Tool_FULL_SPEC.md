# Unity Combat Animation Tuning Tool --- Full Engineering Specification

------------------------------------------------------------------------

# 1. Zielsetzung

Dieses Dokument beschreibt die vollständige Architektur für ein Runtime
Tool zur Bearbeitung von Combat Animation Timing innerhalb eines
gebauten Unity Spiels.

Ziele:

-   Stabilität der Combat Architektur hat höchste Priorität
-   Gameplay Timing ist vollständig data-driven
-   Keine Unity Animation Events für Gameplay Timing
-   Runtime Tool ermöglicht visuelles Tuning durch Tester
-   Animation bleibt reiner Visual Layer
-   Tooling darf Gameplay-Code nicht destabilisieren

------------------------------------------------------------------------

# 2. Architekturentscheidungen (inkl. Begründung)

## 2.1 Keine Animation Events für Gameplay Timing

Warum:

-   Animation Events sind Editor-only Daten
-   Runtime Editing schwierig
-   Versionierungsprobleme
-   Gameplay Logik im Animator versteckt

Stattdessen:

Gameplay Timing wird im Code berechnet.

------------------------------------------------------------------------

## 2.2 Animation = Visual Layer

Animator steuert:

-   Animation Playback
-   Blending
-   Transitions

Animator steuert NICHT:

-   Hit Timing
-   Damage Logic
-   Gameplay State

------------------------------------------------------------------------

## 2.3 Gameplay Anchor

Anchor wird im Code gesetzt:

    attackStartTime = Time.time

Warum:

-   deterministisch
-   multiplayerfreundlich
-   unabhängig vom Animator

------------------------------------------------------------------------

## 2.4 Timing in Frames statt Sekunden

Warum Frames:

-   Combat Design arbeitet in Frames
-   Stabil bei Animation Speed Änderungen
-   Einfach visuell darstellbar
-   Deterministischer als Sekunden

# 4. Datenmodell

## AttackDefinition

``` csharp
[Serializable]
public class AttackDefinition
{
    public string attackId;

    public int totalFrames;

    public int hitStartFrame;
    public int hitEndFrame;

    public float damage;
}
```

Warum totalFrames speichern:

-   Tool unabhängig vom AnimationClip
-   Stabil auch wenn Clip geändert wird

------------------------------------------------------------------------

# 5. Attack Mapping Architektur

Sehr wichtig für langfristige Stabilität.

Problem:

Animation direkt an AttackDefinition koppeln erzeugt später Chaos.

Lösung:

Separate Mapping Layer.

## AttackMapping

``` csharp
[Serializable]
public class AttackMapping
{
    public string animationStateName;
    public string attackId;
}
```

Warum Mapping Layer:

-   Animation kann geändert werden ohne Gameplay Daten zu zerstören
-   Mehrere Animationen können gleiche AttackDefinition nutzen
-   Cleaner Separation of Concerns

------------------------------------------------------------------------

# 6. Runtime Combat System

## Attack starten

``` csharp
attackStartTime = Time.time;
animator.Play(mapping.animationStateName);
```

------------------------------------------------------------------------

## Frame Berechnung

``` csharp
float elapsed = Time.time - attackStartTime;

float animLength = currentClip.length;

float normalizedTime = elapsed / animLength;

int currentFrame =
    Mathf.FloorToInt(normalizedTime * attack.totalFrames);
```

------------------------------------------------------------------------

## Hit Detection

``` csharp
if(currentFrame >= attack.hitStartFrame &&
   currentFrame <= attack.hitEndFrame)
{
    EnableHitbox();
}
```

# 11. Häufige Fehler vermeiden

-   normalizedTime direkt als Gameplay Timing verwenden
-   Animation Events für Gameplay Timing
-   Sekunden statt Frames speichern
-   Animator als Combat State Machine benutzen
